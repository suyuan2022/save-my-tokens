# 派子代理的规则：模板和填法

用户确认了报告里那几件大的派工是模型自己转出去的、要改他的规则文件时用这份文件。下面先讲怎么填，再给模板。

模板里有两类内容：

- **骨架**：没有任何标记的句子。原样用，只做两种改动：换成用户规则文件的语言，换成他文件里对用户的称呼。这些句子是写给能力弱一些的模型也读得懂的：直接对「你」说，每条理由带例子，用平常的词。翻译和改称呼时保持这个写法。
- **占位**：`〔…〕` 括起来的部分。括号里写的是要填什么、从哪取。填完后括号和说明都不留在成品里。

## 怎么填

按顺序做，每一步的材料都来自这个用户自己：

1. **称呼和语言**。读他的规则文件，看它用什么语言、怎么称呼用户（「我」「用户」「the user」、名字……）。模板里的 `〔称呼〕` 全部换成那个称呼；文件里没有直接称呼过用户时，用那种语言里的「用户」。整份规则译成那个语言。
2. **模型和档位**。从扫描报告「子代理：交出去什么、用什么模型」一节取他实际在用的模型：主会话用哪个、派工时指定过哪些。「派给谁」的表只写他在用的模型。他原来的规则里有分工表的，把每一行映射到新表的行里，沿用他原来给那类活定的模型；占位里写的档位只在他没定过时用。原来没有分工表的，只给找材料、请人检查、整件交出去这三行。不为了凑行数引入他没用过的模型。
3. **例子**。三种理由后面的例子和那个改写示范，从他的日志里取：
   - 报告里「像是把整件活交了出去」的名单，取一件当改写示范的原型：标题说的那件整活是什么，其中哪一部分是找材料、可以交出去，哪一部分是判断、该留下。
   - 他常派的小活适合当三种理由的例子：最近的十来件在扫描 json 的 `claude.delegation.small` 里（标题、派给谁、请求数），用 `python3 -c` 只取这一段。那里没有合适的，问用户平时让子代理找什么、查什么、检查什么。
   - 三种理由分开看：哪一种取不到他自己的例子，那一种就用占位里给的通用例子，不替他编场景。任务标题里有私人内容（人名、客户名、内部项目名）时，改写成不带这些的说法。
4. **已有规则**。他的规则文件里已经有管子代理的内容时，逐条交代：这一条保留（放进新规则的哪里）、删除（为什么）、还是被新规则的哪一句替换。和派子代理无关的规矩（比如嵌套几层、审查派几轮）原样保留，接在新规则后面。不整段覆盖。
5. **给用户看 diff**，他同意才改。diff 之外说清三件事：原来哪条规则让模型把整件活转了出去；新规则怎么改了这一点；这一节会从多少字符变成多少字符。新规则通常比原来的表长得多，而且每个会话都带着，这个代价在他点头之前讲。他嫌长时，先删例子，再删「怎么派」一节，「什么时候派」的三种理由和三条确认留着。

填完自查：成品里没有 `〔` 和 `〕`；出现的模型名都是他在用的；取得到他自己素材的地方，例子用的是他的活。

## 模板

```markdown
## 〔节标题：沿用他规则文件里原来那一节的标题；没有就用「子代理」〕

你是〔称呼〕为这次会话专门选的模型。〔称呼〕选你，是要这件事里需要动脑的部分由你本人来做：定计划、中途拿主意、判断结果对不对、下结论。这四样不交给子代理。

子代理（subagent）是帮手，只做你分给它的那一部分活，比如找材料、同时写几处互不相干的代码、帮你检查。它做完把结果交给你，你检查过再用。

### 什么时候派

想把一部分活交给子代理时，先问自己为什么要交出去。理由是下面三种之一才交，都不是就自己做。

1. 要看的材料很多，而你只需要其中一小部分。例：〔两三个例子，取自他常派的找材料类小活。通用例子：在几十个文件里找出一个函数的所有调用位置；在几万行日志里找出报错的那几行；读十篇文章，挑出和问题有关的段落。〕
2. 有几部分活互相不依赖，可以同时做。例：〔一个例子，取自他的项目。通用例子：三个模块各改各的，谁也不用等谁。〕
3. 需要一个没看过你思路的人来检查。例：〔两三个例子，取自他平时请人检查的东西。通用例子：代码写完请人 review；文档写完请人当读者读一遍；请人照原文核对你的摘要有没有走样。〕

决定交出去之后，再确认这部分活同时满足下面三条。有一条不满足，就自己做，或者把它再拆小。

- 你用几句话就能说清楚：要它做什么，材料在哪里，做完交回什么。不需要把前面的对话讲给它听。
- 它做的过程中不需要替你拿主意。
- 它交回来的东西你能很快检查：一份带出处的清单、几段原文、一份 diff、测试通过还是失败。

下面四类活通常不满足这三条，自己做：

- 查一个问题的原因。
- 复盘一件事，下结论。
- 定方案，做规划。
- 方案还没定、需要边写边判断的代码。

做这四类活需要大量材料时，把「找材料」交给子代理，「下判断」留给自己。例：〔一个改写示范，原型取自报告里「像是把整件活交了出去」的名单：先写模型原本想整件交出去的说法，再写改成只交找材料那一部分的说法，最后一句写明判断由谁做。通用示范：你想让子代理「查一下登录为什么偶尔失败」。改成让它「在这三份日志里，找出每次登录失败前后的二十行，把原文和行号交回来」。原因由你读了原文之后自己判断。〕

照着已经定好的步骤改东西，也自己做。

### 派给谁

每次派子代理都写明模型。不写就和主会话用同一个。

| 交给子代理的活 | 模型 |
|---|---|
| 找材料、读材料：找文件、查一个事实、搜代码、联网搜索、读材料出摘要、读日志取证 | 〔他在用的最便宜、够用的模型〕 |
| 请人检查：代码 review、读者测试、照原文核对内容、复查方案 | 〔他的主力模型〕 |
| 〔可选行，他原来的分工表里有、或他的派工记录里常见时才加〕同时做的几部分代码：方案已经定好，每部分改哪些文件、做成什么样都能写清楚 | 〔他的主力模型〕 |
| 〔称呼〕明确说要整件交出去的活，比如说「用后台任务做」「派个 agent 去做」 | 和主会话相同的模型 |

〔他的规则里还给子代理定了别的参数（比如思考强度）时，照他原来的列加一列。〕

### 怎么派

- 给子代理的任务说明里，写明要它交回什么。找材料的：交回原文片段，每段写明出处（哪个文件第几行，哪份日志第几轮），不要它替你下结论。检查的：交回它发现的每一条问题，每条写明依据的是哪段原文或哪处代码。
- 子代理交回来的东西要先检查再用。回复〔称呼〕之前，你自己做完这两件事：读过结论所依据的那几段原文；代码改动看过 diff 和测试输出。
- 〔称呼〕要求整件交出去的活，回复里告诉〔称呼〕这件事交给了哪个模型。

〔他原有的、和上面不冲突的子代理规矩接在这里，原样保留。〕
```

## 为什么是这个骨架

用户问依据时讲这三点：

- 「按活的类型定模型」的表会让模型把「这类活归那个模型」读成「整件交出去」。新规则先回答什么情况才交、交出去的必须是一部分，再回答交给谁。
- 子代理每次交回的是一份有损的摘要，所以判断留在看得到全部上下文的主会话，交回来的东西要对着原文检查。
- 出处：Anthropic 2026-10-22 的文章 Building agents: When to fold subagents into your main agent loop（https://claude.com/resources/articles/building-agents-when-to-fold-subagents-into-your-main-agent-loop）。文中的说法是按上下文划分子代理的活：每件只需要系统其余部分的很少信息，交回一个紧凑的结果；适合的是互不依赖的调研、接口清楚的独立部件、黑盒检查。
